Shadow caster / depth passes are borrowed from URP Lit (characters still cast shadows: verified in frames). Strengths: rimC 0.4, rimA 0.8, rimB 1.6. No cyan/teal anywhere in the colour. No rendering-layer or renderer-feature dependency.

**Findings**
1. **Albedo lift barely helps** (player +0.004 to +0.009; enemy 0 to +0.004 even at x1.4). Not worth a texture-level change; it also risks washing out the albedo.
2. **A warm rim helps measurably and scales with strength:** rim 0.8 improves player separation by 0.038 (B) / 0.041 (A) and enemy by 0.035 / 0.039; rim 1.6 by 0.053 / 0.058 and 0.051 / 0.055. Both cameras behave the same.
3. **Combining adds nothing**: x1.2 + rim 0.8 (-0.050) is no better than rim 0.8 alone (-0.052); x1.4 + rim 0.4 (-0.059) is no better than rim 0.4 x2 would predict. So per your rule ("combined only if both help") the combination is **not recommended**.
4. **Telegraph lift is unchanged (0.137 / 0.048)** in every variant: the character-only change does not touch the floor/telegraph read. (Telegraph colour on the enemy: the emission/tint feedback still works, see regression below.)
5. Even rim 1.6 leaves the figures **darker than the floor** (-0.037 / -0.063); no variant reaches parity. A full fix needs more than a rim.

# FOLLOW-UPS from the Game Director / QA (added to this report)

## (1) The old camera minima (A -76, B +16): cause restated, and what is in the runner now
**My iteration-2 explanation ("the runner never re-aimed the camera, so the run used the wrong pitch") was wrong as stated.** QA is right: the artifact run's minima sit at **frame 0, idle, with a 122-125 px player offset** (A -76 at offset 125, B +16 at offset 122), and every other phase is identical between the artifact run and the corrected run (A: idle min -76 vs 87 only because of frame 0; dodge 23 vs 23. B: dodge 39 vs 39. A2 and C idle are identical in both). `IsoCameraFollow.LateUpdate` re-aims from `offset` every frame, so the whole run was never at a wrong pitch.
**What I can now show by experiment (`Reports/i3_frame0_experiment.txt`, harness `frame0.cs`):** a config change that alters the pitch, applied in the same frame as the first measurement, gives a stale-rotation sample before the first `LateUpdate` has re-aimed the camera: without the explicit re-aim the player offset reads **172 px in the same frame and 50 px from the next frame on**; with the explicit re-aim in `SetConfig` it reads 50 px from the very first frame. A control with the same pitch change (B to A2) shows the same effect (162 vs 45 px, and 47/47 with the re-aim). It also explains why only A (first config, pitch B to A) and B (pitch A2 to B) showed the transient while A2 (same pitch as A) and C (same as B) did not. So the cause is a **one-frame measurement transient (a sample taken before `LateUpdate` re-aimed)**, reproduced; I have not proven it was the *only* difference between the two runs, but all differing numbers are explained by it (frame 0) or by the run-to-run variation below.
**In the runner now:** (a) `SetConfig` / `ApplyConfig` set the camera rotation explicitly (added at iteration 2); (b) **new:** a 2-frame settle (`yield return null` x2) after each config change in `VFRunner.RunCfgs` and at the start of `ArtTestSequenceRunner.RunAll`, so frame 0 is logged only after `LateUpdate` has run. Re-run with the settle (`Reports/i3_settle_cam_*.csv`): frame-0 offset is 1 px for all four configs; minima A 23, B 39, C 130 unchanged.
**Run-to-run variation in the dodge phase (new finding):** the same run with the settle gave **A2 +53 (iteration-2 run: +72; iteration 1 also reported +53) and C +130 (iteration-2 run +130; the artifact run +147)**. Why C's dodge phase was 147 px in the artifact run but 130 px in the corrected one: the two runs diverge from the **attack phase** onward (C first differs at frame 139, 42 differing frames, all of them in attack and later; earlier phases are identical), so the player starts the dodge dash from a slightly different position/offset (65 px in the artifact run vs 53 px in the corrected run at the minimum frame, same speed 22 m/s, same frame). The same attack-phase divergence is visible in A2 and B between the iteration-2 run and today's re-run (first differing frame 117, phase attack, positions differ by 1-6 px). The cause of the nondeterminism in the attack phase (animation/lunge, physics or enemy AI timing under the Editor) is **not isolated**. Practical consequence: **the dodge-dash minimum is a range, not a single number: A +23, A2 +53 to +72, B +39, C +130 to +147** (A and B reproduced exactly in every run after the fix, A2 and C varied). The recommendation ordering (A2 over B) is unchanged, but treat A2 as "+53 to +72".

## (4) Why the rim light failed (read-only investigation, no shared asset changed)
**Cause found: I set the wrong property.** `PC_RPAsset.asset` has `m_SupportsLightLayers: 1` (confirmed) and the project has 8 rendering layers. URP's forward lights take their layer mask from **`UniversalAdditionalLightData.renderingLayers`** (`ForwardLights.cs:699`), not from `Light.renderingLayerMask`; the core property is only the shadow-culling mask that URP writes itself (`SyncLightAndShadowLayers`). My iteration-2 test wrote only `Light.renderingLayerMask = 2`, so the URP data stayed at its default (Default layer = bit 0), and the floor (renderer mask 1, bit 0) was lit. All floor, wall and character renderers have `renderingLayerMask = 1`; the key light's URP layers = 1.
Direct test (`lightlayers.cs`, runtime-created spot light, nothing saved, brightness = mean luma of a patch, torso and floor patch next to the player):
| Case | floor patch next to player | player torso |
|---|---|---|
| no light | 0.422 | 0.434 |
| URP layers = Default | 0.565 (lit) | 0.526 |
| **iteration-2 method (only Light.renderingLayerMask = 2)** | **0.565 (floor lit: the failure)** | 0.527 |
| **URP layers = 2, characters bit0 + bit1, floor bit0** | **0.422 (floor unlit)** | **0.526 (lit)** |
| URP layers = 2, characters bit0 only (negative control) | 0.422 | 0.430 |
| URP layers = 8 (nobody has it) | 0.422 | 0.428 |
**So per-light rendering layers work with the existing shared URP asset and renderer; no renderer change is needed.** What blocked it was my test, not the pipeline. I had labelled the (a) test a failure caused by the renderer; that claim is **withdrawn**.
Retest of test (a) with the correct API (spot lights behind/above each character, URP layers 2, character renderers bit0 + bit1, intensity 14 and 6, warm white, orig materials): floor luma at the player unchanged (0.409 / floor mean 0.381), telegraph lift unchanged (0.137 / 0.048); player separation -0.090 to **-0.081 (14) / -0.087 (6)** at B and -0.097 to -0.088 / -0.091 at A; enemy -0.114 to -0.111 / -0.113 (B). The layer-masked light rim works as designed but gives **much less than the material fresnel rim** (rim 0.8: -0.053 player, -0.067 enemy at B) at these simple settings; spot placement/cone were not tuned. Both are art-test-only and reversible; the choice is a stylistic one for the CD (a light-based rim follows the key/placement and can be restricted to the actors; the material rim is view-based). Raw rows: `Reports/i3_evidence_rows.csv`, frames `Captures/char_i3_evidence_frames/`.
